# От включения ПК до просмотра

| Решение | Причина и последствие | Как проверить при реализации |
|---|---|---|
| Один координатор на Go и SQLite, сервер отдаёт также статический браузерный клиент на JavaScript | Один адрес для преподавателя, транзакционный журнал и инвентарь переживают перезапуск. Для первого грида достаточно браузерных API | Перезапустить сервер между двумя входами, сверить места и журнал |
| Системная служба на Go под OpenRC, отдельный процесс сессии на Python с XRandR/X11 | Узел доступен до входа. Только пользовательский процесс получает Xauthority. Библиотеки захвата и кодеки проверяются на Calculate | Войти, выйти и сменить пользователя при работающей службе |
| HTTPS/WSS для управления и сигнализации, WebRTC для крупного просмотра | Браузер использует штатные механизмы видео и шифрования. Для сети без прямого маршрута может понадобиться локальный TURN | Проверить тип выбранной ICE-пары и закрытие трека после отзыва доступа |
| Гипотеза для миниатюр — уменьшенные JPEG по выходам через координатор | Простое декодирование и независимые обновления. Полоса и декодирование растут с числом видимых мест | [Сравнительный эксперимент T03](../tasks/T03.md) |

```text
браузер ── HTTPS/WSS ── координатор ── существующий mTLS/WSS ── системная служба
                                                               │ локальный Unix-сокет
                                                               процесс X11
браузер ◀──────────── WebRTC через LAN или локальный TURN ──────┘
```

1. Puppet привязывает идентичность узла к инвентарю. При загрузке системная служба сама открывает исходящее соединение к координатору, предъявляет сертификат, объявляет возможности и поддерживает heartbeat. Сервер сверяет сертификат с nodeId. IP-адрес может меняться. Грид строится из закреплённых мест даже при отсутствии соединений.
2. KDE запускает процесс в локальной физической X11-сессии. Служба проверяет учётные данные Unix-сокета и соответствие активной локальной сессии и seat. В реестр попадают новый sessionId, ревизия раскладки и выходы. Захват читает видимый рабочий стол, включая окно xrdp и методичку рядом. Терминальный сервер в этом пути не участвует.
3. Браузер входит по HTTPS. Координатор проверяет преподавателя и разрешённую аудиторию при подписке на грид. Браузер сообщает видимые места. Уменьшенные кадры идут от процесса через локальную службу и исходящий канал к координатору, затем через WSS к подписчику. Медленный подписчик получает последний кадр. Канал команд имеет отдельную очередь и ограничение очереди превью.
4. Клик открывает просмотр. Запрос указывает узел, сессию, ревизию и монитор либо весь рабочий стол. Координатор заново сверяет привязку, право просмотра и доступность выбранного выхода. Он выдаёт короткоживущее одноразовое разрешение, связанное с преподавателем, целью и режимом. Процесс проверяет разрешение при установлении сеанса через доверенный канал. SDP и ICE проходят через координатор. Медиа идёт по согласованному WebRTC-соединению. ICE требует достижимости между браузером и ПК либо доступа обоих к локальному TURN. Внешний STUN в базовой сети не требуется.
5. Кнопка управления создаёт отдельный запрос с проверкой права control. Просмотр сам по себе не разрешает ввод. События ввода идут через авторизованный канал управления координатора к сессии. Выданное разрешение связано с текущей сессией и ревизией. Сервер журналирует преподавателя, аудиторию, цель, режим, время и исход, без содержимого экрана и нажатий.
6. При возврате в грид останавливаются интерактивный трек и ввод. При logout процесс закрывает захват, служба очищает sessionId. При изменении геометрии инвалидируется прежняя ревизия. При разрыве, отзыве права или истечении аренды локальный таймер прекращает ввод и медиа, освобождает клавиши и кнопки. Сервер удаляет подписку, скрывает кадры прежней сессии и отмечает узел offline по таймауту heartbeat. После восстановления требуется новая авторизация.

Системные действия проходят из браузера через координатор по уже установленному каналу к службе, пользовательские передаются проверенной сессии. Право проверяется для каждого целевого места. Область и срок операции фиксируются при создании запроса. [Правила действий](../actions/README.md) определяют повторы и неопределённый результат.

## Решение T11. Координатор на учительском ПК

Один экземпляр обслуживает одну аудиторию и использует два слушателя. Браузер открывает HTTP и WebSocket строго на `127.0.0.1:8768`. Сетевой слушатель на порту 8767 принимает только `/source` по mTLS и связывает сертификат агента с местом из инвентаря. Для ученических ПК сохраняются прежние адрес, порт и формат сообщений.

Преподавателю достаточно открыть портал в браузере учительского ПК. Локальные процессы получают доступ с правами `teachers.local` из политики кабинета, поэтому портал рассчитан на выделенный учительский ПК. Журнал пишет `local` как субъект просмотра и управления. Локальный слушатель проверяет `Host`, WebSocket проверяет `Origin`, а страница по умолчанию запрещает встраивание. Адрес UI не публикуется через прокси. Миниатюры идут через этот же координатор, а WebRTC использует согласованный сетевой путь.

Разделение маршрутов, клиентский сертификат агента и защиту браузерного входа проверяет `python3 server/live_acceptance.py --listeners-only`. Полный сценарий подтверждает миниатюры, WebRTC и отзыв доступа на синтетическом источнике. [Развёртывание и проверка в классе](../ops/live.md)

Для доступа из меню «Внешние сайты» администратор может разрешить встраивание с адреса доверенного Nextcloud. Установщик записывает `nextcloud_origin` из инвентаря в локальную политику координатора, а координатор использует его в `frame-ancestors` страницы портала. Браузер обращается к тому же loopback-слушателю с правами `teachers.local`. Nextcloud получает возможность встраивать интерфейс, поэтому указывайте адрес сервера, которому доверяете. Полный сценарий `python3 server/live_acceptance.py` проверяет в Chromium запрет с другого адреса, декодирование превью и полноэкранное видео внутри тестовой HTTPS-страницы. [Настройка для кабинета](../ops/ssh/README.md)

## Решение T15. Питание одного ученического ПК

Локальный портал принимает команду с того же origin при наличии права `system.power` на аудиторию. Координатор сверяет `nodeId` с инвентарём и действующей привязкой сертификата, затем отправляет запрос по уже открытому каналу mTLS. Системная служба сама объявляет поддерживаемые команды и обрабатывает их до входа в KDE. Сообщения пользовательской сессии не могут объявить системную возможность или подтвердить её выполнение.

Служба резервирует `requestId` в локальном SQLite перед вызовом фиксированного метода `PowerOff` или `Reboot` в login1. Учительский ПК хранит отправку и исход в аудите. Потеря подтверждения отображается как неопределённый результат, повторной отправки нет. `python3 server/power_acceptance.py` проверяет этот путь от Chromium до подменённого вызова login1. [Физическая проверка](../tasks/T15.md)

## Решение T04

Для первой вехи выбран JPEG через WSS. В серии с четырьмя движущимися выходами получено 7,8 кадра/с на самом медленном выходе и p95 возраста 22 мс при исходящих 1213 кбит/с. Предел числа мест проверяется на физическом классе. [Измерения T03](../experiments/previews/README.md)

T05 использует [preview.v1](../contracts/preview/README.md) для миниатюр и WebRTC для крупного просмотра. Приёмка контракта входит в общую проверку: она воспроизводит запоздавшую доставку и завершение декодирования после смены источника.

## Развёртывание с рабочего места администратора

Для класса с действующим доступом SSH по ключам предусмотрена [установка из локального Git](../ops/ssh/README.md). Оператор управляет одной аудиторией и хранит её CA на своей машине. Git bundle фиксирует одну ревизию для координатора и ученических ПК. Сервер и узлы получают отдельные роли службы, Chromium открывает локальный портал на выделенном учительском ПК с правами teachers.local. Права меняются атомарной заменой policy.json. Для проверки повторить установку, сравнить отпечатки, дождаться online и пройти физическую приёмку T05.

Установка по SSH добавляет общий автозапуск KDE на ученическом ПК. PID и UID соединения берутся из SO_PEERCRED. Служба допускает владельца активной локальной пользовательской X11-сессии seat0 по login1 и повторно проверяет идентификатор сессии во время соединения. Сокет доступен для подключения локальным процессам, его каталог принадлежит службе. Смена ученического логина сохраняет сертификат узла и привязку к месту. Проверка на стенде описана в [T12](../tasks/T12.md).

Администратор готовит системные пакеты на узлах заранее. При установке скрипт проверяет необходимые команды и login1. Python-модули устанавливаются через pip в окружение из локального кэша узла. Ключ кэша учитывает интерпретатор, ABI и файлы зависимостей. Ревизия получает ссылку на окружение после успешной установки. Проверка переиспользования описана в [T12](../tasks/T12.md). При проверке на стенде запустите установщик на узле без одной из обязательных команд и проверьте, что диагностика указывает узел и команду.

При расширении кабинета установщик дописывает места новых узлов в SQLite одной транзакцией. Развёрнутые места сохраняют координаты и связи с nodeId. Координатор перечитывает рассадку при перезапуске. Проверка двух установок с добавлением узла описана в [T12](../tasks/T12.md).

Перед доставкой релиза и сертификатов установщик читает идентификатор аудитории из SQLite координатора через SSH в режиме только для чтения. Это предотвращает частичное обновление при несовпадении идентификаторов. При записи инвентаря проверка повторяется в транзакции. [Приёмка T12](../tasks/T12.md)

Параметр pip_proxy в инвентаре применяется к установке Python-зависимостей на всех ПК кабинета. Установщик доставляет адрес через стандартный ввод SSH и задаёт PIP_PROXY для процесса pip. Если учреждение предоставляет собственный индекс Python, pip_index_url задаёт адрес API Simple через PIP_INDEX_URL. При явно выбранном HTTP-зеркале pip получает доверенный хост на время установки. Маршрут проверяется по журналу индекса или прокси при подготовке нового окружения. [Инструкция по SSH](../ops/ssh/README.md)

При выборочном обновлении полный инвентарь задаёт рассадку, а --only-node ограничивает доставку кода ученическим узлам. Установщик использует существующий CA и переносит привязки сертификатов остальных узлов из действующей политики координатора. Координатор обновляется вместе с тестовыми узлами. Проверка смешанных ревизий описана в [T12](../tasks/T12.md).

Установщик добавляет обе службы OpenRC в уровень запуска `default` и проверяет их состояние после перезапуска. Сетевая зависимость `net` в OpenRC необязательна. Координатор открывает локальный портал даже при сбое сетевой службы, а ученический агент повторяет попытки подключения до восстановления сети. Итоговая проверка по SSH запрашивает главную страницу портала и `/state` на учительском ПК и ждёт подключения обновлённых узлов. [Проверка повторного запуска на стенде](../tasks/T12.md)

После запуска службы узла установщик атомарно переключает принадлежащую root ссылку на ревизию пользовательского агента. Агент с обновлённым автозапуском замечает её изменение, завершает старое соединение и выполняет новую ревизию с прежним PID и учётными данными графического сеанса. Проверка login1 остаётся частью допуска. [Проверка обновления в том же сеансе](../tasks/T12.md)
