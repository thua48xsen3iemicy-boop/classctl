# Работа в classctl

Начните с [README](README.md), [архитектуры](docs/architecture.md), [очереди](tasks/README.md) и файла конкретной задачи. Проверьте git status, зависимости задачи и границы изменений. Сохраните чужие правки. README компонента определяет его обязанности, [схема v1](contracts/v1.schema.json) определяет форму сообщения, [правила контракта](contracts/README.md) задают межсообщенческие ограничения.

Публичное изменение сначала запишите отдельной задачей с производителями, потребителями и планом совместимости. Назначьте одного владельца схемы. Обновляйте схему, версию, положительный и отрицательный примеры, проверку, потребителей и заметку для оператора одной согласованной поставкой. Зависимую работу начинайте после интеграции контракта. Локальные детали компонента выбирайте самостоятельно.

Меняя границу доверия, транспорт, модель полномочий или способ развёртывания, добавьте решение в [архитектуру](docs/architecture.md) с причиной, эксплуатационным последствием и воспроизводимым способом проверки.

Запустите `python3 checks/verify.py` и проверки приёмки из задачи. Новые внутренние ссылки пишите обычными относительными Markdown-ссылками на файлы. Готовая задача оставляет рабочее дерево с относящимися к ней изменениями и воспроизводимым результатом. В отчёте укажите команду, наблюдение, тип источника, ограничения среды и конкретную оставшуюся стендовую проверку. Документацию и задания пишите по-русски, код и идентификаторы по-английски.
