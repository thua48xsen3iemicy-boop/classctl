# T03. Доставка миниатюр аудитории

## Цель

Проверить 5–10 отображённых кадров/с на **каждом** видимом выходе при движении. При статике требуется подтверждение свежести. Для медленного подписчика важны ограничение очереди и возраст действительно показанного кадра. Задание и входные данные: [T03](../../tasks/T03.md), [инвентарь](../../contracts/examples/room.json), [состояние](../../contracts/examples/status.json).

## Гипотезы до измерений

Независимые JPEG упрощают позднюю подписку и замену ожидающего кадра. Межкадровое сжатие VP8 должно экономить полосу на движущемся окне поверх статического фона. Предполагаем один преподавательский браузер. До стендового прогона выяснить число мест и одновременно видимых карточек, разрешения и ориентацию мониторов, модели ПК, версии браузера, доступную полосу uplink и возможность прямой ICE-пары.

## Повтор

Linux, Python 3.12, Chromium, OpenSSL и coturn (команда turnserver). Нужны TCP/UDP на loopback. Из корня репозитория в активированном окружении выполнить:

```sh
cd experiments/previews
python -m pip install -r requirements.txt
python run.py --out /tmp/previews-baseline.jsonl
python run.py --out /tmp/previews-limited.jsonl --seats 24 --visible 2 --outputs 2 --scenarios moving outage --mbps 1
python report.py /tmp/previews-baseline.jsonl
python report.py /tmp/previews-limited.jsonl
```

Каждый выходной файл должен быть новым. Число мест задаёт размер инвентаря, генератор обслуживает первые видимые места. Параметры --source W H, --thumb W H, --fps, --duration (секунды) и --outputs 1 2 меняют профиль серии. --mbps ограничивает темп отправки медиаданных источником, ноль отключает ограничитель. Это программное распределение времени отправки. Полосу Ethernet и потери пакетов стенд не эмулирует.

## Метод

Один процесс ученика генерирует кадры всех подписок. На одинаковом синтетическом фоне движется окно; изображение уменьшается одним алгоритмом перед кодированием. Номер кадра записывается в пикселях, индекс потока связан с местом, sessionId, layoutRevision и monitorId в сырых данных. JPEG с качеством 75 идёт через два WSS-соединения с координатором. Координатор держит на выход один отправленный кадр до ACK и один заменяемый ожидающий. Для WebRTC используется отдельная дорожка на выход и общий BUNDLE. В измеренном Chromium политика запрещает прямой UDP. ICE-статистика подтверждает локальный TURN/TCP и браузерный декодер VP8. Для каждого прогона запускаются новые процессы, временный сертификат, профиль Chromium и индивидуальные учётные данные TURN.

- **moving** — непрерывное движение. **static** — три начальных кадра, затем только подтверждения проверки подписанных выходов. Сигналом служит WSS-сообщение от процесса захвата.
- **slow** — просмотр замедлен на 350 мс. JPEG удерживает кадр до отрисовки и подтверждения. Браузер WebRTC продолжает декодировать, а приложение реже выбирает последний кадр для показа. Это сравнение пользовательского результата при медленном потребителе.
- **outage** — в средней трети прогона источник прекращает выдавать кадры и подтверждения. Браузер самостоятельно отмечает stale через 500 мс после последней проверки. Дополнительный тест в ограниченной серии закрывает WSS и PeerConnection, ждёт 700 мс, заново подписывается и ждёт изображения каждого выхода.

## Единицы и границы измерения

FPS — минимум по видимым выходам за весь интервал, включая остановки. Возраст — от начала генерации кадра до завершения рисования в canvas, включая масштабирование и декодирование. Время физического вывода на монитор сюда не входит. Источник и браузер используют часы одного хоста. Оценка погрешности — лучший из семи запросов времени в Chromium с запасом 1 мс на округление. p50/p95 объединяют отображённые кадры. «Без показа» включает замены, пропуски при выборке и кадры на границе остановки.

CPU указан в процентах одного ядра, RSS — пиковая сумма MiB по дереву процессов при выборке каждые 200 мс. Общие страницы процессов Chromium могут учитываться несколько раз. Серверный столбец включает координатор и локальный TURN. Источник обслуживает все места одним процессом. Трафик ↓/↑ указан в кбит/с по полезным байтам WSS и счётчикам транспорта WebRTC. Для TURN оценка построена по байтам обоих концов соединения. Заголовки TCP/IP, TLS, сбор кандидатов и установка HTTP-соединений учитываются неполно. Значение 0 означает менее 0,5 кбит/с либо отсутствие прикладных данных этого направления.

Очередь/замены — максимум числа ожидающих кадров координатора JPEG или глубины входной очереди отдельной видеодорожки и общее число вытеснений. Внутренние очереди ОС и кодеков отдельно не измерялись. stale/возврат — интервал от последнего подтверждения до stale и от первого возобновлённого подтверждения до показа нового кадра. В сыром JSONL одна строка на прогон с конфигурацией, инвентарём, временами захвата/отрисовки, подтверждениями, ресурсами процессов и статистикой RTC.

## Измерения и решение для T04

[Основная серия](results.md) и [сырые данные](series.jsonl). Синтетический источник 1280×720, миниатюры 320×180, 8 кадров/с, два видимых места и один или два выхода на место. Каждая серия длилась около пяти секунд на общем Linux-хосте AMD EPYC 9V74 с квотой двух CPU и Chromium 156.0.8078.79.

При четырёх движущихся выходах JPEG показал минимум 7,8 кадра/с с p95 возраста 22 мс, WebRTC — 6,3 с p95 156 мс. Исходящий поток источника составил соответственно 1213 и 119 кбит/с. На медленном JPEG-подписчике p95 вырос до 481 мс, ожидающая очередь достигла четырёх кадров, 103 кадра были заменены. У WebRTC в этом сценарии p95 составил 172 мс. На статике в каждом прогоне браузер получил 40–41 подтверждение, последние изображения показаны в начальные 300 мс. При паузе источника все четыре сценария обнаружили stale за 510–521 мс.

Для первой сквозной вехи выбрать JPEG/WSS и закрепить в T04 подписку на видимые выходы, идентичность сессии и ревизии, замену старого ожидающего кадра и независимые подтверждения статичного изображения. Причины — достигнутая частота и меньший p95 в обычном гриде. WebRTC сохранить кандидатом для ограниченной полосы и крупного просмотра. Порог переключения требует более длинных повторных серий. Два видимых места не определяют ёмкость аудитории.

На реальном Calculate повторить матрицу с двумя физическими выходами, X11-захватом статичной методички, прокрутки и окна xrdp. Измерить возраст при синхронизации между хостами, CPU каждого ПК, физические интерфейсы сервера и браузер преподавателя. Проверить при штатном числе видимых мест прямой ICE и локальный TURN, пропадание линка, новую сессию и смену раскладки мониторов.

**Ограничение 1 Мбит/с.** При инвентаре на 24 места и четырёх подписанных выходах минимум при движении составил 5,7 кадра/с для JPEG и 6,4 для WebRTC. После полного закрытия соединений новая подписка показала все четыре выхода за 193 мс для JPEG и 347 мс для WebRTC, считая от начала повторного открытия страницы. Это единичные наблюдения. Программный ограничитель JPEG замедляет генератор при отправке, а WebRTC может вытеснить кадр перед кодированием. [Результаты серии](limited.md) и [исходные измерения](limited.jsonl).
